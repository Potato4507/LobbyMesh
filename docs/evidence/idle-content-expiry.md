# Idle content expiry and closed-owner cleanup — 2026-10-29

Source inspection found that the15-minute content-age rule was enforced only during history reads or other traffic. An idle backend could retain text longer if its renderer stopped polling. Added a single unref'd expiry timer to each direct messenger and desktop messaging owner. No timer exists until state is retained. The earliest retained message/metadata expiry schedules the next sweep; one sweep discards due entries and schedules the next remaining deadline, or clears the timer when empty. Later arrivals cannot postpone an earlier deadline. Close cancels scheduling permanently.

Direct history expires at receivedAt+900000; desktop incoming/outgoing views at at+900000. Reply hints expire at their existing120000ms deadline. Direct duplicate fingerprints retain their original freshness-aware expiry; they are not removed early to free content. Clear still retains bounded duplicate/rate metadata and removes plaintext. Timers make idle cleanup independent of renderer requests; on-access expiry still runs as a second check. Timing follows the existing validated wall-clock age rules and JavaScript scheduling. OS suspension, event-loop delay or clock changes can affect when callbacks run; this is not secure erasure of process memory or a hard real-time guarantee.

Also corrected two lifetime gaps:

- Block previously denied history reads and cleared renderer state, but backend conversation/direct-history plaintext remained until ordinary expiry. Block now removes both copies immediately while preserving replay fingerprints, so removing the block and explicitly authorizing later cannot replay the old accepted text. Earlier conversation-block evidence established denial/UI clearing, not backend memory deletion; that stronger historical wording is superseded by this change/test. Ordinary permission revocation retains its established hidden-history behavior, with automatic age expiry.
- An inbound handler can synchronously accept a request, yield while awaiting its result, then resume after service.close. It now checks closed before retaining the reply hint, preventing post-close cache repopulation.
